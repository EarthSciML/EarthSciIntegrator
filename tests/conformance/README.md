# Conformance suite

Shared by the Julia and Rust implementations (architecture §12, spec/README.md).

| Directory | Contents | Checked by |
|---|---|---|
| `run-configs/valid/` | Run configs the schema must accept. `reseact`, `eqice` and `eqwefic` are architecture §4.4's three examples, completed with the `esm_integrator`, `model` and `operators` keys the architecture's fragments omit; their schedules are unchanged. The eqice and EqWeFiC operator selectors use illustrative component names until M4b and M7 bind them to the real documents. | `validate_schemas.py`; the Julia and Rust test suites also check their `esm_integrator` version |
| `run-configs/invalid/` | Run configs the schema must reject, one defect each, named for the defect. | `validate_schemas.py` |
| `plans/valid/`, `plans/invalid/` | The same for `plan.json`. The valid plan is hand-written and reseact-shaped; it exercises the schema only. | `validate_schemas.py` |
| `plans/fixtures/` | The M2 planner fixtures, tier 1 (spec/plan.md §9); layout below. | `validate_schemas.py` (structure); the Julia and Rust planners against the goldens |
| `plans/refusals/` | Inputs the planner must refuse, one refusal each, with the expected code (spec/planner-errors.json); layout below. | `validate_schemas.py` (structure); the planners |
| `toys/` | The toy problems of spec/toy-problems.md §1 as esm 1.3.0 documents (spec/toy-problems.md §4.1). | `validate_schemas.py` (EarthSciAST 0.9.0 loads, validates and flattens them) |
| `m1/cases.json` | The M1 conformance cases on the hand-written toy problems (spec/toy-problems.md), generated by `m1/make_cases.py`. | `validate_schemas.py` (structure); the Julia and Rust test suites run them; CI checks the file matches its generator |
| `m1/compare_results.py` | The `cross_language` check: compares the Julia and Rust result files and tapes. | CI's cross-language job, on the result files the Julia and Rust jobs upload |
| `m1/reference/` | Reference results for cases without an exact solution. | `validate_schemas.py` (structure) |
| `m2/cases.json` | The M2 end-to-end cases: the M1 cases on the `toys/` documents, planned and run, checked by `toy_equivalence` against the same implementation's M1 run (spec/toy-problems.md §4.2), and the data-input cases (§4.4–§4.6), checked against `m2/reference/`. Generated by `m2/make_cases.py` from `m1/cases.json`. |
| `toys/make_data.py`, `m2/reference/` | The data files of the data-input toy problems (`toys/data/data_decay/`, `toys/data_monthly/`, `toys/data_points/`) and the reference results of their exact solutions. `python tests/conformance/toys/make_data.py --check` regenerates them and compares decoded values (not the netCDF bytes, which HDF5 stamps). | CI | `validate_schemas.py` (structure); CI checks the file matches its generator; the runtimes run them |

Each `invalid/` directory has an `expected-errors.json` naming, per fixture, the schema keyword that must fail and where; a fixture that fails anywhere else has a second defect and is reported. Run tier 0 locally with `python tests/conformance/validate_schemas.py` (needs `jsonschema` ≥ 4.18); add `--require-esm`, as CI does, to fail rather than skip when the `earthsci-ast==0.8.0` Python package is not installed (spec/plan.md §0.2).

## Planner fixtures: `plans/fixtures/`

One directory per model:

```
plans/fixtures/<fixture>/
  model.esm                      the model (toy fixtures point at ../../../toys/ instead)
  <case>.run.json                one run config per case; its `model` is relative to it
  expected.md                    a section "## <case>" per case: what the golden must contain
  <case>.expected-plan.json      optional: the case's whole plan.json written by hand in RFC 8785
                                 form, with the derived documents' sha256 set to 64 zeros
  <case>.golden/                 the golden, written by the Julia planner (tools/plan-goldens.jl):
    plan.json
    derived/*.esm
    validation/<operator>.bandvalues.json    Julia's ForwardDiff band values; the harness compares Rust's against them (spec/plan.md §8.2)
```

**Goldens.** The Julia planner writes `<case>.golden/`; a reviewer checks it against `expected.md` (and `<case>.expected-plan.json` where there is one) before it is checked in; the Rust planner must then write the same `plan.json` and `derived/*.esm` byte for byte (spec/plan.md §9). Every case with a `<case>.run.json` has a golden; a missing one fails both test suites (`julia/EarthSciIntegrator.jl/test/planner_fixtures.jl`, `rust/earthsci-integrator-planner/tests/fixtures.rs`), it is not skipped. Both suites compare `plan.json` and `derived/*.esm` byte for byte and the band values as §8.2 says: each suite evaluates its own band Jacobian at each sample's `t` and `u` in the golden's band-value file, and must have the same structural (row, column) set, each value within $10^{-10}$ of its row's largest magnitude. The file must have three samples at §5.5.1's quantiles of the interval, a `u` naming every DOF, and no (row, column) listed twice. `expected.md` describes contents, not bytes: the terms and their provenance and locality, each operator's locality, radius, `writes`, `reads`, structure and stiffness, the resolved schedule, step, partition, precision, derived documents and validation entries.

**Regenerating the goldens.** From the repository root:

```
julia --project=julia/EarthSciIntegrator.jl tools/plan-goldens.jl                     # every case, in place
julia --project=julia/EarthSciIntegrator.jl tools/plan-goldens.jl periodic_stencil    # one fixture
julia --project=julia/EarthSciIntegrator.jl tools/plan-goldens.jl reseact_shaped/named # one case
julia --project=julia/EarthSciIntegrator.jl tools/plan-goldens.jl --out OUTDIR        # elsewhere, to diff against the checked-in ones
```

The script rewrites `plan.json`, `derived/` and `validation/` of each `<case>.golden/`, drops `plan.report.json` (package versions and measured errors, not part of a golden), and compares the plan with `<case>.expected-plan.json` where there is one. A regenerated golden that changes is reviewed against `expected.md` again before it is committed; the Rust planner must then match it.

| Fixture | What it exercises |
|---|---|
| `pointwise_chemistry` | a reaction system lifted pointwise, block-diagonal structure and its Markowitz plan, stiffness from `reaction_systems`, the `Rosenbrock23`/`Rodas4` tolerance rule |
| `periodic_stencil` | PPM-like advection reaching 3 cells upwind and 2 downwind, the periodic seam as literal wrapped indices, the footprint read from bands, halos and a rank/tile grid |
| `column_contraction` | a PBL-mean-like full-column `faq` contraction (column locality), Gershgorin stiffness, TRBDF2 with a banded solve |
| `reseact_shaped` | reseact's shape: chemistry, transport and mixing as three `operator_compose` contributions; operators by provenance and by default locality; `auto` and named schedules |
| `unnamed_lift` | a pointwise lift onto a grid no index set is declared for: `flatten`'s synthetic index set `_liftdim1_4` as the lifted states' shape, the default axis and every derived document's `index_sets` (spec/plan.md §6.1.3) |
| `forced_column` | data-fed parameters (D87): a two-record field reached through a `param_to_var` coupling and blended in time, a `const` scalar, an `ic` read from data, an unused field with no default; the plan's and operators' `forcing`, the derived documents' forcing slots and `data_sources` stubs, the band-value files' `forcing` (spec/plan.md §4.1, §5.5.1, §6.3, §8.2) |
| `inverse_decay` | a state with no `default`, started only by its `ic` equation, that the band coefficient divides by: the Jacobian document gives it the `default` `1.0` (spec/plan.md §6.2 item 4, D89) |
| `cross_component_term` | a `couple` term that reads two other components' variables, which provenance alone cannot place (D65), selected by provenance label and by owner |
| `toy_robertson`, `toy_photostationary_cells`, `toy_advection_reaction` | the toy problems' `.esm` versions under their M2 cases' run configs |

## Refusal fixtures: `plans/refusals/`

One directory per refusal, holding `run.json` and, when the refusal is about the model, `model.esm`; other runs point at a fixture's model. `expected-codes.json` gives, per directory, the `code` (listed in spec/planner-errors.json) and `at`, the JSON pointer into `run.json` the refusal must report (`/model` for a refusal about the model). A planner passes a refusal fixture when it writes no plan and reports that code at that pointer; the message is not compared.
